# Concept-answer grounding and json_object fallback (v2 review)

The three issues from the v1 review are all addressed in commit `213813b`. Concept reference answers are now grounded in the concept's own source chunk text via a new pure `buildConceptContext` helper, resolving each `KeyConcept.sourceChunkIndexes` back to its chunk text (capped at 4000 chars) and falling back to the book summary only when no chunk resolves. Both live providers route their JSON completions through a new `createJSONWithFallback` that retries once without `response_format` when a model rejects the parameter. The `grok-3-mini` default now carries a comment stating it's expected to be overridden via `XAI_MODEL`. All zod contracts, the `LLMProvider` interface, and the mock path are untouched.

Watch for: nothing blocking. One minor asymmetry — the `OpenAIProvider` fallback retry keeps its terse default system message ("valid JSON only") which lacks the explicit no-code-fence wording `XAIProvider` uses, but `parseJSONResponse` strips fences regardless so it degrades cleanly (confirmed).

**Verdict**: APPROVED

## High-level view

The grounding gap is closed. `generateQuestions` now takes an optional `chunks?: TextChunk[]`, and `src/app/api/analyze/route.ts` passes the same `book.chunks` that `analyzeBook` consumed, so the concept-to-chunk index mapping is consistent end to end. `buildConceptContext` builds a `Concept: … / Context: …` message from the concept's actual source text and falls back to `analysis.summary` only when chunks are absent or no index resolves — the case the mock keyless path hits, which keeps determinism intact.

The `json_object` fallback is a network-free, injectable abstraction. `createJSONWithFallback` tries the JSON-object request and, on a format-unsupported error, retries once with `response_format` dropped while preserving model, temperature, and the JSON-only system instruction. `isResponseFormatUnsupportedError` is deliberately conservative: it triggers only on a 400 that mentions the format parameter, or a statusless message that both mentions it and describes it as unsupported — so a 429 or auth error won't cause a pointless retry.

The model-drift note is documented rather than fixed, appropriate given the `XAI_MODEL` override. No API key is hardcoded, constructors still throw only on an empty key and never touch the network at import, and the new helpers are pure/injectable so the added tests stay keyless.

### Concept context resolves real chunk indexes, with a safe fallback

`buildConceptContext` maps `chunks` into an index→text lookup, walks the concept's `sourceChunkIndexes` in sorted order, and concatenates chunk text up to `CONCEPT_CONTEXT_CHAR_LIMIT` (4000). The fallback to `summary.trim()` fires only when the joined source text is empty — no chunks passed (the mock/keyless path) or none of the indexes resolve. This makes the `conceptAnswerSystemPrompt()` "use only the provided context" instruction truthful on the keyed path: the model now sees the text the concept was drawn from, not a book-level summary about an unrelated chunk.

`route.ts` feeds `book.chunks` to both `analyzeBook` (which produces the `sourceChunkIndexes` via `[...entry.chunkIndexes].sort(...)`) and `generateQuestions`, so the indexes a concept carries always refer to a chunk present in the lookup — no silent misses. The char cap slices per-chunk against the remaining budget, so a single oversized chunk is truncated rather than dropped, covered directly by the `CONCEPT_CONTEXT_CHAR_LIMIT + 500` test.

### response_format fallback is targeted and preserves the JSON instruction

`createJSONWithFallback` drops only `response_format` on retry:

```ts
const { response_format: _dropped, ...withoutFormat } = params;
return create(withoutFormat);
```

The `messages` array — including the system message with `JSON_ONLY_INSTRUCTION` (xAI) — is carried through unchanged, so the retry still steers the model toward a bare JSON object, and `parseJSONResponse` handles residual fences/prose. The gate in `isResponseFormatUnsupportedError` is the safety property: it returns `true` only for a 400 mentioning `response_format`/`json_object`, or a statusless message that mentions the parameter *and* reads as unsupported/invalid/unknown. A 429 that happens to mention the format string returns `false`, so transient rate limits aren't swallowed into a silent parameter-stripping retry. The retry is one-shot; a second failure propagates.

The `OpenAIProvider` fallback path uses its default "responds with valid JSON only" system message, which doesn't explicitly forbid code fences the way `XAIProvider`'s `JSON_ONLY_INSTRUCTION` does. Both parse through `parseJSONResponse` so the OpenAI path still recovers from fenced output — a consistency nit, not a correctness bug.

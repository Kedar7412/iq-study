# Grok (xAI) provider and grounded analysis prompts (v1 review)

Swaps the analysis pipeline off the deterministic mock LLM and onto Grok when a user-supplied `XAI_API_KEY` is present. A new `XAIProvider` reuses the OpenAI SDK against `https://api.x.ai/v1` (xAI is OpenAI-compatible), a shared `parseJSONResponse` helper hardens the JSON layer against fenced/prose-wrapped model output, and the terse mock-era system prompts are replaced with grounding-first prompts that constrain the model to the supplied text. The factory auto-selects xAI when the key is set and otherwise falls back to the mock, so the app stays keyless-green. The LLMProvider interface and all downstream zod schemas are untouched.

Watch for: the concept-answer step is grounded in a 2-4 sentence summary rather than the source text, so its "use only the provided context" instruction promises more grounding than the payload delivers (confirmed). Both live providers request `response_format: json_object`, which some Grok models reject with a hard 400 — there is no fallback (likely).

**Verdict**: NEEDS_CHANGES

## High-level view

`XAIProvider` is a near-copy of `OpenAIProvider` differing only in `baseURL`, default model (`grok-3-mini`), and a JSON-only instruction appended to the system prompt. Both live providers now route responses through `parseJSONResponse`, which strips code fences and extracts the first balanced `{...}` object before validation, so a chatty model no longer breaks the zod parse.

Selection precedence in `getLLMProvider` is explicit-first (`LLM_PROVIDER=xai|openai` + matching key), then auto-select xAI on a bare `XAI_API_KEY`, then mock. Constructors validate the key but never touch the network, so all paths are safe to reach keyless.

The grounding rewrite is where behavior and intent diverge. The per-chunk prompt receives the actual chunk text, so its "work strictly from the excerpt" instruction is honored. The per-concept prompt tells the model to answer "using only the provided context" and forbids outside knowledge, but the user message it grounds against is `${concept}. ${analysis.summary}` — a single short book-level summary, not the concept's source chunks. On a real model that instruction will either be under-fed (thin answers) or quietly violated (the model fills gaps from its own knowledge), which is the exact "makes no sense / talks about anything" failure the task set out to kill.

The API surface adds three optional env vars (`XAI_API_KEY`, `XAI_MODEL`, `LLM_PROVIDER=xai`) documented consistently in `.env.example` and README, with the key correctly flagged as a secret. No key is hardcoded.

<summary>Issues (3)</summary>

1. **Concept-answer grounding gap** — `generateQuestions` feeds only `concept + book summary` to a prompt that claims "use only the provided context," so the answer isn't grounded in the concept's source text. Pass the relevant source chunk(s) (via `keyConcept.sourceChunkIndexes`) into the user message so the instruction matches the payload.
2. **`response_format: json_object` with no fallback** — both live providers hard-require `json_object`; xAI/Grok models that don't support it return a 400 that surfaces as a failed analysis. Confirm the default `grok-3-mini` supports it, and/or catch the format-unsupported error and retry relying on the prompt + `parseJSONResponse`.
3. **`grok-3-mini` default may drift** — the hardcoded default model is a moving target across xAI's lineup; if it's ever retired, keyed users break. Low priority given `XAI_MODEL` override, but worth a comment noting the default is expected to be overridden in production.

### Concept-answer prompt promises grounding the payload doesn't provide

`conceptAnswerSystemPrompt()` instructs the model to explain the concept "as it is used IN THIS book, using only the provided context" and to "not invent facts or bring in outside knowledge that the context does not support." But the call site grounds it in very little:

```ts
const draft = await provider.completeJSON(
  `${kc.concept}. ${analysis.summary}`,          // concept + one book-level summary
  (raw) => questionDraftSchema.parse(raw),
  { system: conceptAnswerSystemPrompt(), temperature: ANALYSIS_TEMPERATURE },
);
```

`analysis.summary` is the first chunk's 2-4 sentence summary (see `analyzeBook` reduce step), not the concept's own source text. For any concept that doesn't appear in chunk 0, the "provided context" contains nothing about it, so a compliant model produces a thin or empty answer and a non-compliant one falls back on its own knowledge — the outside-knowledge drift the task exists to prevent (confirmed). The per-concept path already knows where each concept came from (`KeyConcept.sourceChunkIndexes`); threading those chunk texts into the user message would make the instruction truthful. The per-chunk `chunkAnalysisSystemPrompt` does not have this problem — it receives `chunk.text` directly.

### json_object response format is a hard requirement on both providers

`XAIProvider.completeJSON` (mirroring the OpenAI one) sends `response_format: { type: "json_object" }`. If the configured Grok model doesn't accept that parameter, xAI returns a 400 and the whole analyze/generate call fails rather than degrading (likely — depends on the exact model, not traced against a live API). The new `parseJSONResponse` plus the appended `JSON_ONLY_INSTRUCTION` already make the pipeline robust to prose-wrapped output *without* `response_format`, so a targeted catch that retries without the format field would turn a hard failure into a soft one. Worth confirming `grok-3-mini` supports `json_object` before shipping the default.

# Supabase-backed stores fix the "User not found." onboarding bug (v1)

Onboarding failed in production because the three data stores were in-memory module singletons: a fresh Vercel serverless isolate served the onboarding POST with an empty user map, so `getUserStore().saveProfile(session.sub, …)` matched no row, returned `undefined`, and the route emitted `User not found.` (404). This change adds hosted-Supabase-Postgres implementations behind the unchanged `UserStore`/`BookStore`/`ReviewStore` interfaces, selects the backend at store-construction time via `isSupabaseConfigured()`, and keeps the existing in-memory classes as the automatic keyless fallback when `SUPABASE_URL`/`SUPABASE_SERVICE_ROLE_KEY` are absent. A server-only admin client (service_role, bypasses RLS), pure camelCase↔snake_case mappers with keyless unit tests, and `.env.example`/README updates round it out. The interface semantics the onboarding 404 depends on are preserved: `saveProfile` returns `undefined` when no row updates.

Watch for: the Supabase admin client is **not memoized in production** (`getSupabaseAdmin` only caches on `globalThis` when `NODE_ENV !== "production"`), so every store operation constructs a fresh `SupabaseClient` on Vercel — confirmed.

**Verdict**: APPROVED

## High-level view

The fix keeps callers untouched: each store module still exports the same interface, types, and `get*Store()` accessor, and just chooses `Supabase*Store` vs `InMemory*Store` at module load based on whether both env vars are set. Because the interfaces were already async, no route handler changed. The in-memory classes are preserved verbatim, which keeps the 79 existing route/session tests green keyless.

The onboarding-bug-critical semantics are reproduced in SQL terms. `saveProfile` issues an `UPDATE … .eq('id', id).select('*').maybeSingle()`, so a missing user yields `undefined` (the exact signal the 404 relies on) rather than a fabricated record. `BookStore.get`/`saveAnalysis` push ownership into the query with `.eq('user_id', userId)`, so a non-owner gets `undefined`, matching the in-memory tenant-isolation guarantee. `list` orders `created_at desc`.

RLS is enabled with no policies, the server uses the service_role key that bypasses RLS, and the app keeps its own cookie/JWT auth. The client module is server-only, reads the key only from `process.env`, and is never imported by a client component.

The one behavioral wrinkle is the admin client's production memoization gap: the store singletons themselves are module-level consts and survive per isolate, but `getSupabaseAdmin()` rebuilds a client on every call in production because the global cache write is gated behind non-production.

### Preserved semantics that gate the onboarding 404 and tenant isolation

```
saveProfile(id, profile):
  UPDATE users SET learning_profile = profile
  WHERE id = id
  RETURNING *            -> .select('*').maybeSingle()
  no row  -> data === null -> returns undefined -> route emits 404
```

Durability alone would fix the empty-isolate case, but the `undefined`-on-no-row contract is what the route branches on, and the Supabase path reproduces it via `maybeSingle()` on the `RETURNING` set rather than fabricating a record. The same shape backs `BookStore.saveAnalysis`. For reads, `get` and `saveAnalysis` fold ownership into the query with a second `.eq('user_id', userId)`, so a non-owner is indistinguishable from a missing row (`undefined`) — the store, not the caller, enforces isolation, matching the in-memory `book.userId !== userId` check. `list` applies `.order('created_at', { ascending: false })` for most-recent-first.

### Mapping conventions: null↔absent and bigint→number

A DB `null` optional column (`learning_profile`, `curriculum`, `analysis`, `questions`, `analyzed_at`) maps to an **absent** property via `if (row.x != null)` guards, not a `null` value, so round-tripping a not-yet-analyzed book reproduces the original object exactly (`toEqual` plus explicit `not.toHaveProperty` assertions confirm this). Writes send `?? null` so clearing works. `created_at`/`analyzed_at` pass through `Number()` on read, covering the string-ish bigint some Postgres drivers return. `reviewDeckFromRow` defaults a null `cards` column to `[]`, safe given the column default is `'[]'`.

### Secret hygiene and the server-only boundary

The service_role key is read only from `process.env`; a grep for `eyJ`/`sb_secret`/`sb_publishable`/`service_role_key` finds nothing in `src` — the publishable/service_role identifiers live only in the task's `context.json`, not in shipped source. The client module is imported exclusively by the three store modules (all consumed by `nodejs`-runtime route handlers), and no `"use client"` file reaches it, so the RLS-bypassing key cannot leak into a browser bundle. No `NEXT_PUBLIC_*` var was introduced, and the docs avoid instructing the reader to run migrations from this repo.

### Admin client rebuilt per call in production

```ts
const cached = globalForSupabase.__iqStudySupabaseAdmin;
if (cached) return cached;
const client = createClient(...);
if (process.env.NODE_ENV !== "production") {
  globalForSupabase.__iqStudySupabaseAdmin = client;   // never runs in prod
}
return client;
```

In production the cache is never populated, so each `getSupabaseAdmin()` call — one per store operation — constructs a new `SupabaseClient`. The store singletons survive per isolate (module consts), but the client they call does not, defeating the memoization the doc comment claims ("created lazily and memoized"). Not a correctness bug and won't fail keyless verification, but it adds per-request client construction overhead on the exact runtime this change targets. Memoize on a module-level variable unconditionally, or drop the `NODE_ENV` guard on the cache write. Confidence: confirmed.

### Test coverage

The 14 new mapper tests cover, per entity, object→row→object round-trip, null-column→absent-property, bigint→number, and camelCase→snake_case column placement — each would fail if the mapping were reverted. Not tested: the `Supabase*Store` classes themselves (query construction, ownership `.eq` filters, `maybeSingle` undefined-on-no-row). That's a deliberate consequence of no live DB, and the semantics are instead guaranteed structurally by the mappers plus the query shape; still, a future edit dropping a `.eq('user_id', …)` would not be caught by any test.

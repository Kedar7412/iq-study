# IQ Study MVP: keyless upload → analyze → adaptive study loop (v1)

IQ Study is a from-scratch Next.js 16 / React 19 app that takes an uploaded book (`.txt`/`.md`/`.pdf`), analyzes it into ranked exam questions weighted by a learner-supplied curriculum, profiles the learner with a VARK-style questionnaire, and drives an SM-2 spaced-repetition loop whose ordering and interval adapt to that profile. The whole stack runs keyless: a deterministic `MockProvider` stands in for OpenAI, and `AUTH_SECRET` falls back to a documented dev-only key. The domain math (SM-2, question scoring, profile scoring, concept-map linking) is factored into pure, well-tested functions, and the auth primitives (bcrypt hashing, `jose` HS256 JWT in an httpOnly cookie) are sound. Watch for: the entire ingestion/analysis API surface is unauthenticated and books are a single global pool, so any caller can upload, analyze, read, and study any book by id — this breaks both the security posture and the per-user product promise (confirmed).

**Verdict**: NEEDS_CHANGES

## High-level view

The read path and the analysis path diverge on auth. `/api/study/*` and `/api/onboarding` verify the session server-side, but `/api/upload`, `/api/analyze`, and `/api/books/[bookId]` do not — the `proxy.ts` matcher only gates page routes (`/upload`, `/books`, `/study`, `/onboarding`), never `/api/*`. So the core ingestion and results endpoints are reachable with no credentials at all.

Books are stored in a single process-wide `Map` keyed only by a generated `bookId`, with no owner field. Any authenticated user (and, per the gap above, any anonymous caller) who knows or guesses a `bookId` can read its content, re-analyze it, and build a study deck against it. For a product whose whole pitch is "*your* book, *your* curriculum, *your* brain," this is a correctness gap, not just a hardening nit.

The domain logic is the strong part of this change: the SM-2 scheduler, local question-probability heuristic, deterministic profile scoring, and concept-map linking are all pure and covered by behavioral tests. The keyless goal is met cleanly — `getLLMProvider` only constructs the OpenAI client when both `LLM_PROVIDER=openai` and a key are present, and never throws otherwise. Auth primitives are correct (bcryptjs cost 10, HS256 via `jose`, httpOnly + `secure`-in-prod cookie, generic 401 with no user enumeration, `AUTH_SECRET` production requirement documented in bold).

The in-memory stores are a documented, accepted MVP limitation, and the README's persistence caveat covers books, users, and the surprise that accounts and decks vanish across serverless invocations. One product-quality edge remains: `scoreProfile` normalizes over only the answers submitted, so a client that posts a single answer still gets a "valid" profile.

4. **Curriculum-overlap scoring is all-or-nothing** — question probability and analysis boost treat curriculum overlap as a binary 0/1 on a single-word match, so a one-word coincidence scores the same as a full topic match. Consider a graded overlap signal; low priority.

### The `/api/*` surface is ungated while pages are gated

`proxy.ts` gates the protected *pages*, and its matcher is explicit:

```ts
export const config = {
  matcher: ["/upload/:path*", "/books/:path*", "/onboarding/:path*", "/study/:path*"],
};
```

No entry covers `/api/*`. The study and onboarding route handlers compensate by calling `getSession()` themselves and returning 401, but `/api/upload`, `/api/analyze`, and `/api/books/[bookId]` do not — none of them import `getSession`. The three endpoints that carry the actual book content are reachable with no cookie at all: anyone can POST a file to `/api/upload`, trigger `/api/analyze`, and GET the analyzed questions from `/api/books/[bookId]`. The asymmetry is the tell — the study routes prove the intended posture is "verify server-side," and these three simply don't. The fix is the same `getSession()` guard the study routes already use (confirmed).

### Books are a global pool with no owner (IDOR)

`StoredBook` records `bookId`, `meta`, `text`, `chunks`, `curriculum`, `analysis`, `questions` — but no user id. `InMemoryBookStore` keys everything by `bookId` in one `Map` shared across the whole process:

```ts
async get(bookId: string) { return this.books.get(bookId); }
```

`generateBookId()` uses `Date.now()` + 8 random base36 chars, so ids aren't trivially enumerable, but they are shared verbatim in URLs (`/books/[bookId]`, `/study/[bookId]`) and API responses. Once a logged-in user has any `bookId`, the study routes build a deck against it because they only check that a session exists, never that the session owns the book. Combined with the ungated upload/analyze/read path above, there is no tenant isolation anywhere in the book lifecycle. This defeats the per-user premise of the product. The review decks *are* correctly keyed per `(userId, bookId)`, so the fix is to carry an owner id on the book record and enforce it wherever a `bookId` is resolved (confirmed).

### Question scoring and curriculum overlap

`probability = clamp01(0.6*importance + 0.4*(overlap ? 1 : 0))`, matching the documented heuristic, computed locally so it's reproducible under the mock. The weakness is that curriculum overlap is binary and matches on any single normalized word (`conceptMatchesCurriculum` splits the concept and returns true if *any* word is a curriculum term), and `analyzeBook` applies a flat `+0.3` boost on the same all-or-nothing basis. A concept that shares one common word with the syllabus scores identically to one that matches a whole topic, which can pull loosely-related concepts to the top of the "ultra high probability" list. A graded overlap (fraction of concept words matched, or topic-level match weighted higher than word-level) would track the product intent better (likely).

### Profile scoring accepts partial submissions

`scoreProfile` normalizes each sensory dimension as a fraction of *style-bearing answers actually submitted*, and `validateAnswers` only throws when zero answers are provided. A client that submits a single answer (`{ q1: "q1a" }`) therefore gets a fully-formed profile with `visual: 1` and everything else 0. The onboarding UI presumably submits all ten, but the API doesn't enforce that, so a truncated or buggy client silently produces a skewed profile that then drives every downstream adaptation. Requiring the full set of question ids (or a minimum count) before scoring would close this (confirmed).

### Test coverage

The suite is genuinely behavioral, not smoke tests: SM-2 progression/floor/reset, profile normalization and deterministic tie-breaks, adaptive ordering for kinesthetic vs. neutral learners, interval multiplier direction, token tamper/wrong-secret rejection, and deterministic chunking. Not tested: the route handlers themselves — precisely where the missing auth checks and the missing ownership enforcement live, so no test currently asserts that an anonymous caller is rejected from `/api/upload` or that a user can't study another user's book. Route-level tests would have surfaced the auth gap and would guard the fix.

## Response (review-fix pass)

All four issues were **fixed**; none were deferred.

1. **Unauthenticated ingestion/analysis API (BLOCKING) — FIXED.** Added a
   server-side `getSession()` check returning `401` to `POST /api/upload`,
   `POST /api/analyze`, and `GET /api/books/[bookId]`, matching the pattern the
   study/onboarding routes already use. The `proxy.ts` matcher was intentionally
   left gating pages only; the API is now gated per-route (public auth routes
   such as login/register must stay reachable, so blanket `/api/*` proxy gating
   was avoided).

2. **Books not scoped to a user / IDOR (BLOCKING) — FIXED.** `StoredBook` now
   carries a required `userId` owner, set from the session at upload time. The
   `BookStore` interface is ownership-aware while staying clean:
   `get(bookId, userId)`, `list(userId)`, `saveAnalysis(bookId, userId, result)`.
   The in-memory store returns `undefined` for a non-owner, so
   `GET /api/books/[bookId]`, `POST /api/analyze`, and both study routes return
   `404` to anyone but the uploader. This mirrors the per-`(userId, bookId)`
   scoping the review decks already use.

3. **Partial questionnaire yields a valid profile — FIXED.** `validateAnswers`
   now requires an answer for **every** questionnaire item (after validating
   ids), throwing a clear message that `POST /api/onboarding` surfaces as `400`.
   `scoreProfile` stays pure. The onboarding UI already enforced completeness
   client-side, so no UI change was required.

4. **Curriculum overlap all-or-nothing — FIXED (graded).** Introduced
   `curriculumOverlapScore` in `[0, 1]`: a full-concept match scores `1.0`; a
   partial match scores `matchedWords / totalWords` scaled by
   `PARTIAL_MATCH_CEILING = 0.9`, so an all-words-but-not-a-listed-topic concept
   approaches but never reaches a full match, and a single coincidental word
   contributes only a small fraction. `analyzeBook` applies
   `CURRICULUM_BOOST * score`; `generateQuestions` applies
   `CURRICULUM_WEIGHT * score`. `conceptMatchesCurriculum` is retained as a
   boolean view (`score > 0`). Heuristic documented in-source.

**New tests.** `src/app/api/__tests__/routeAuth.test.ts` (route-handler tests:
`401` unauthenticated + `404` non-owner + owner success across
books/analyze/study, with `getSession` mocked over the real in-memory store);
`src/lib/analyze/__tests__/curriculumOverlap.test.ts` (graded overlap ordering
and ceiling); and expanded `learningProfile.test.ts` (rejects incomplete /
accepts complete questionnaire).

**Verification (all keyless, Node 22 via nvm):** `npm test` = 79 passed,
`npm run typecheck` clean, `npm run lint` clean, `npm run build` succeeds.
